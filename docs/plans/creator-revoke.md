# 创建者主动撤销：功能方案与原型

日期：2026-10-21。状态：正式功能已实现并完成本地验收。本轮未合并、未部署。

原型基线：`main@de83988`。正式实施同步至 `main@57f226c`，保留已上线的二维码结果组件。分支：`codex/creator-revoke-prototype`。

## 目标与首版范围

创建者发错链接或希望提前结束分享时，可以通过独立管理链接撤销，不需要联系管理员。

- 用户已确认：文本、代码和文件分享都支持。
- 匿名使用，无须账号。持有完整管理链接就拥有该条分享的撤销权限。
- 首版只有撤销，不加入编辑、续期、密码修改、恢复、个人分享列表或管理链接找回。
- 撤销不可恢复。需要继续分享时重新创建，得到新的分享链接和管理链接。
- 规划轮交付方案和可交互原型；用户已授权正式接入文本、文件创建与撤销，并运行测试和本地浏览器验收。

成功标准：用户能够分清“发给接收者的链接”和“自己保存的管理链接”，完成确认撤销，并理解撤销的实际边界。

## 成熟产品依据

- [PrivateBin 官方 FAQ](https://github.com/PrivateBin/PrivateBin/wiki/FAQ#how-can-i-delete-a-paste)：创建成功后提供分享链接和删除链接；删除链接需要自行保存，没有凭证无法自主提前删除。借鉴其匿名持链接管理方式，不增加账号系统。
- [Wormhole 官方 Roadmap](https://wormhole.app/roadmap)：已提供在到期前删除文件。借鉴“提前结束分享”的单一操作；该来源未说明其权限凭证机制，不将它作为独立管理链接的依据。

## 用户流程与界面规则

### 1. 创建成功

保持当前“链接已生成”弹窗和关闭后保留结果卡片的行为。两处使用同一份结果组件。

1. 主区域为“分享链接”，说明“发给接收者”，保留复制和查看分享。
2. 次区域为“私人管理链接”，提供“复制管理链接”和“进入管理页”。
3. 管理链接附近提示：“自行保存。持有此链接即可撤销分享，请勿发给接收者。丢失后无法自行找回。”
4. 不提供“复制全部”，不把管理权限拼进分享链接、二维码或访问密码。已有文本自动复制只复制分享链接；文件保持手动复制。
5. 两个复制动作各自反馈成功或失败；失败时链接仍可选中手动复制。
6. 管理链接只随创建结果提供。关闭弹窗不丢失当前结果；刷新或“创建另一条”后，不承诺找回原管理链接。

### 2. 私人管理页

标题“管理这次分享”。显示类型、语言或文件名、有效期、剩余次数和是否有访问密码，供创建者确认目标。

- 不展示文本正文、密码正文或文件内容，不提供领取或下载按钮。
- 访问、刷新、页面预取、查看管理状态均不消耗次数，也不执行撤销。
- 分享有效时显示“分享中”和“撤销分享”。此页面不需要管理员登录，不需要再次输入分享密码。
- 缺失或错误管理凭证时不展示分享摘要，只提示“管理链接无效或分享已失效”，引导检查创建时保存的完整链接。

### 3. 确认并撤销

点击“撤销分享”后打开确认对话框。默认焦点在“继续分享”，Escape 和关闭操作都取消撤销。

> 撤销这次分享？
>
> 撤销后，新的查看和下载请求将被阻止，且无法恢复。已经显示、复制或下载的内容，以及已经开始传输的文件，无法收回。

按钮：“继续分享”“确认撤销”。确认后显示“正在撤销…”，禁用重复提交。取消和仅打开对话框都不会改变分享。

只有服务端确认已停止分享后才显示“分享已撤销”。移除撤销按钮，提供创建新分享入口。请求失败时保留错误和重试入口，不提前报成功。

### 4. 接收者继续访问

撤销完成后，新的正文领取和文件下载均失败。公开页显示“分享已失效”，不展示正文或下载按钮。

公开页没有必要区分创建者撤销、管理员删除及记录清理，不新增长期状态记录。已有页面中已经显示的内容不会被远程抹除，已完成领取或开始传输的内容不在撤销控制范围内。

## 状态与异常

| 情况 | 管理页反馈 | 可执行动作 |
| --- | --- | --- |
| 有效管理链接、分享有效 | 分享中，展示摘要 | 确认撤销 |
| 撤销请求处理中 | 正在撤销… | 等待，阻止重复提交 |
| 当次撤销成功 | 分享已撤销 | 创建新分享 |
| 返回时确认尚未撤销的请求失败 | 撤销失败，请重试 | 继续分享或重试 |
| 网络断开，无法判断结果 | 暂时无法确认撤销结果，请重试 | 重试前重新读取状态 |
| 记录仍在、已过期或次数用尽 | 分享已过期／次数已用完，无需再撤销 | 创建新分享 |
| 记录已删除、错误凭证或缺少凭证 | 管理链接无效或分享已失效 | 检查完整管理链接／创建新分享 |
| 管理信息加载失败 | 暂时无法加载分享状态 | 重试加载；不显示有效态或撤销成功 |
| 文件访问已停止、磁盘清理失败 | 分享已撤销 | 用户无须重复操作，服务端保留日志并按现有机制清理 |

若撤销响应丢失，重新检查发现记录已不存在，只能确认当前不可用；不能声称准确知道它由谁撤销。撤销成功页再次打开或刷新也不保证识别具体结束原因。

## 正式实现建议

以下为已确认的实施设计，实际完成和验证结果另行记录。

### 数据和管理权限

在 `pastes`、`file_shares` 各增加一个可空 `management_token_hash` 字段，不新增用户表或管理记录表。

- 新建分享时使用 Node 内置 `crypto.randomBytes(32)` 生成随机管理凭证，编码为 base64url。数据库只存 SHA-256 摘要。
- 创建响应增加 `managementUrl`；分享 URL 和既有规则不变。管理链接形如 `/manage/text/{id}#凭证` 或 `/manage/file/{id}#凭证`。
- 片段 `#` 后的凭证由浏览器读取，再放入 API 的 `Authorization: Bearer …` 请求头。这样管理凭证不会成为页面请求路径或常规访问日志的一部分。
- 管理凭证只授权对应类型和 ID，不能跨分享使用。访问密码仅允许领取内容，不提供撤销权。
- 已有分享该字段为 `null`，不根据公开链接补发管理权，也不补造旧分享凭证。需要管理能力时重新创建分享。
- 沿用现有依赖和单例数据库，无新依赖、新签名系统、管理员会话、额外锁或凭证轮换机制。

### API 草案

均沿用 `success()` / `error()` 的响应形式，创建及管理响应使用 `Cache-Control: no-store`。

| 接口 | 成功响应与行为 |
| --- | --- |
| `POST /api/pastes` | 既有数据增加 `managementUrl`，凭证摘要随新记录保存 |
| `POST /api/files` | 既有数据增加 `managementUrl`，沿用上传失败回滚 |
| `GET /api/manage/{kind}/{id}` | 验证凭证后返回 `kind/id/status/createdAt/expiresAt/remaining/hasPassword` 和对应语言或文件名；不返回正文、密码、存储路径或凭证摘要 |
| `DELETE /api/manage/{kind}/{id}` | 验证凭证后停止分享，返回 `{ revoked: true }` |

`kind` 只接受 `text` 或 `file`。缺失／错误凭证、无对应记录时统一返回 404 和 `MANAGEMENT_UNAVAILABLE`，不泄漏目标摘要。真实内部错误保留日志并返回 500，不包装成已撤销。

DELETE 重试不会恢复或重复消耗分享。记录已被删除时返回统一不可用状态；不为重复返回“已撤销”而保留墓碑，也不把找不到记录当成服务故障。请求结果不确定时先读取当前状态：仍有效才允许再次撤销，不可用则提示分享已失效、具体原因无法确认。

### 复用的删除与并发边界

- 文本：将 `app/api/admin/pastes/[id]/route.ts` 的“删除文本和对应密码失败记录”事务提为 `src/lib/paste.ts` 的业务函数。管理员和管理链接接口共用业务函数，不互调 HTTP 接口。
- 文件：直接复用 `src/lib/file-share.ts` 的 `deleteFileShare()`。它先标记 `pending_delete` 停止领取，再删除文件和记录；文件删除失败会标记 `delete_failed` 并保留诊断。
- `deleteFileShare()` 返回 `found: true, deleted: false` 时已经阻止访问，管理接口可确认撤销；不能声称磁盘已清空。现有 `file-cleanup-job.ts` 每五分钟重试，无新清理任务。
- 不新增 `revokedAt`、撤销墓碑或生命周期状态机。只在当次成功响应后明确显示“已撤销”；记录清理后统一失效。
- 文本领取和文件下载已有事务内的可用性复查。以领取事务和撤销写入的先后为准：撤销先完成则拒绝交付，领取先完成则不能收回。
- 文件读取与磁盘删除可能竞争。针对文件 IO 失败补回归；仅在再次查询确认该分享已经停止时返回失效，其他 IO 错误仍保留原诊断。
