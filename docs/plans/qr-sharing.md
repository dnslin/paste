# 二维码分享：规划与交互原型

日期：2026-10-21。基线：`de839887688c392ecf75e0f63e33684fdee90afa`。状态：第二版原型已获用户批准，正式接入和上线前验证已完成。部署结果另存于对应提交的服务器发布目录。

设计预览：[二维码分享原型](http://127.0.0.1:3331/prototype/qr-sharing)。正式功能分支：`codex/qr-sharing`。

## 目标与范围

让用户在文本或文件生成链接后，能用手机扫码打开同一条分享。第一版仅增加二维码展示，不增加账号、历史记录、撤销、系统分享、二维码下载或分享参数配置。

本功能按用户要求先规划及原型，再接入正式文本和文件分享。用户已明确批准第二版布局，并授权回归测试通过后合并和部署。原型入口为 `/prototype/qr-sharing`，只使用演示数据，不调用分享 API；正式功能位于首页创建成功后的弹窗和保留结果。

## 产品规则

1. 文本和文件采用同一个二维码区块，成功弹窗默认直接显示；关闭弹窗后，结果卡片继续保留同一个二维码。
2. 正式接入时只编码创建 API 返回的完整 `url`。不编码正文、文件字节、访问密码或管理凭据，不新建另一条分享。
3. 二维码仅在浏览器本地生成，不将链接发送给外部二维码服务。
4. 生成、显示、复制二维码对应链接不请求内容领取或下载接口。扫码打开页面后，密码、有效期及显式领取/下载计次继续沿用既有规则。
5. 无论分享是否受密码保护，二维码都只编码访问链接。受保护的分享在二维码旁简短提示“密码请单独提供”。
6. 二维码与原链接同时有效或失效，不承诺恢复失效分享，也不轮询链接状态。
7. 复制链接和查看分享继续可用；文本成功弹窗保留自动复制，文件仍手动复制。“创建另一条”才进入下一次创建。

## 界面方案：第二版

用户反馈第一版不好看，感觉不对称。截图可确认：标题与摘要左对齐，二维码和底部操作居中，700px 的卡片与 200px 白色二维码之间形成大片空白。长链接、整排按钮和二维码分成三个宽度，视觉重心断开。

本轮采用 `frontend-design` 和 `design-with-clarity`。二维码是这张分享卡片的主体；标题、分享摘要、二维码和规则共用中轴，链接与复制组成一个控件，后续操作形成对等的底部一行。收窄卡片，统一弹窗与保留结果的尺寸与间距。

- 配色：底色 `#0a0a0b`、卡片 `#121214`、控件 `#1a1a1e`、正文 `#fafafa`、辅助文字 `#a1a1aa`、复制强调色 `#f59e0b`；二维码保持黑白。
- 字体：沿用 Geist；成功标题 20px，摘要与操作 14px，规则与 URL 12px；URL 使用 Geist Mono。
- 布局：弹窗和保留卡片均为最大 448px；手机统一左右 16px 外边距，内部 20px，桌面内部 24px。二维码保持 192px、四模块留白，白色外框 208px。
- 层级：成功标题 → 语言或文件名 → 二维码及扫码说明 → 链接/复制 → 到期、次数与密码规则 → 查看分享/创建另一条。
- 链接从左向右阅读，超长地址省略显示，悬停可查看完整地址，辅助技术读取完整链接，复制始终使用完整值。两个底部动作等宽，复制是唯一琥珀色操作。
- 长文件名居中换行，避免单独一小截后缀留在下一行。密码提示与分享规则放在一起，扫码说明只表达扫码操作。
- 首页网格降低对比；不增加装饰、渐变、Logo 水印、额外二维码弹窗或新功能。
- 短视口沿用弹窗内部滚动，关闭、复制及继续创建必须可达；关闭后回焦点到保留卡片的复制按钮。

```text
                    Paste
              分享文本、代码和文件
          ┌───────── 448px ─────────┐
          │        链接已生成        │
          │      语言 / 文件名       │
          │                         │
          │        ┌──────┐         │
          │        │ QR码 │         │
          │        └──────┘         │
          │     手机扫码打开分享      │
          │                         │
          │ [访问链接…] [复制链接]   │
          │        到期时间          │
          │      次数 · 密码规则     │
          │ [查看分享] [创建另一条]  │
          └─────────────────────────┘
```

开工前核对：整体延续 Paste 的编辑器风格；只调整二维码原型的内容关系和几何比例。原先的大容器与独立分割线不再沿用，新的集中布局服务于复制链接和扫码这两个具体任务。正式创建页面及全站设计规范不改动。

## 原型边界与体验路径

原型控制栏与产品画面分开，提供文本/文件切换及“查看成功弹窗”。初始直接展示结果卡片，便于评审二维码；弹窗可以关闭，卡片仍保留。继续创建使用预填演示数据模拟下一次生成。

演示二维码编码本地原型的绝对地址及接收场景片段。点击“查看分享”可进入既有接收原型组件，文本与文件场景各自对应，不落到不存在的线上分享。演示密码会在原型控制栏中注明。

演示数据不是真实业务分享。二维码能够编码并解码，不等于已经完成手机跨设备连通验收；本机回环地址不能作为公网分享地址。正式实施后须使用真实 API 链接再做手机扫码验收。

## 技术与文件边界

- 现有 React 19、Radix、Button/Dialog、剪贴板 hook、接收原型和样式继续复用；不修改 `src/components/ui/*`。
- 当前依赖及锁文件没有二维码编码库；Lucide 的二维码图标不能代替可识别二维码。
- 采用 `qrcode.react@4.2.0` 的 `QRCodeSVG`，其公开接口支持 React 19、尺寸、纠错等级、留白和辅助技术标题。使用 `level="M"`、`marginSize={4}`，不自行编写编码算法。原型与已批准的正式结果组件均使用该依赖。
- 原型页面：`app/prototype/qr-sharing/page.tsx`。
- 原型组件及测试：`src/components/qr-sharing-prototype/`。
- 规划、截图及验证记录：`docs/plans/qr-sharing.md` 和 `docs/plans/qr-sharing-prototype/`。
- 正式接入候选：共享二维码展示组件以及现有链接结果区。优先一次接入覆盖文本/文件、弹窗/保留结果，避免四份重复逻辑；不改 API 或数据库。

```tsx
<QRCodeSVG value={url} size={192} level="M" marginSize={4}
  role="img" title="分享链接二维码" />
```

## 执行顺序

1. 固定范围、二维码内容及界面层级，写出本规划。
2. 在独立原型路由完成真实二维码、文本/文件结果、弹窗/保留结果与演示接收跳转。
3. 补充核心交互测试，验证二维码链接对应、关闭后保留、类型切换与复制反馈。
4. 在隔离的本地预览核对桌面、手机和短视口，检查真实二维码内容、焦点及横向溢出；交付原型供用户确认。
5. 第二版已确认，接入正式流程，再对真实文本和文件分享做二维码解码、打开链接及计次验证，验证通过后合并及部署。

## 正式接入与上线

- `src/components/share-result/share-created-content.tsx` 提供共享结果内容及弹窗。文本、文件与设计原型共用二维码、链接复制、规则和底部操作，删除旧的重复结果展示。
- 文本和文件仍由各自创建入口处理原 API 响应、密码状态及次数。共享结果只接收完整 URL、显示名称、到期时间、次数和密码保护布尔值，不接收密码正文。
- 二维码与两个查看链接均使用原 URL，无额外 fetch、预取或下载；仅文本成功弹窗自动复制。
- 回归先取得真实 RED：正式入口 19 项中有 6 项因缺少二维码失败；随后同一组入口测试及新共享组件测试共 25/25 通过。
- 全量测试、类型检查、代码检查和生产构建已通过；隔离预览已核对正式文本/文件生成、关闭保留和二维码目标。
- 合并前进行独立代码评审和一次测试敏感性检查。部署使用已合并的明确提交、专用镜像、空卷回归，再完整备份并只切换生产镜像；保留原密钥、管理员配置、数据卷和本地端口绑定。
- 上线后使用自建测试文本和文件检查实际 HTTPS 链接、二维码内容、密码、领取/下载次数以及文件字节；清理本轮自建记录，不操作既有用户分享。实体手机扫码与软件解码及打开链接分开记录。
